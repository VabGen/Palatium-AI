# MAX PRO LEVEL 2026 — Техническое задание Palatium AI

> Когнитивный шлюз с агентной памятью и многоагентной оркестрацией.

## 0. Статус документа

Это **описательное ТЗ** — обоснование архитектурных решений и целевая картина
системы. Оно не заменяет `.cursor/rules/*.mdc` — те нормативны и обязательны

Канон проектирования — [Anthropic Engineering](https://www.anthropic.com/engineering);

## 1. Принцип 2026: brain ≠ hands ≠ session

Ключевая идея года (Anthropic, *Scaling Managed Agents*) — не «богатый контекст
побеждает», а разделение трёх абстракций, которые раньше склеивали в один
процесс:

| Абстракция | Что это | В Palatium |
|---|---|---|
| **Brain (LLM-цикл)** | Модель, принимающая решения на шаге | Конкретный агент (`BaseAgent.run`) |
| **Harness** | Цикл «вызвать модель → выполнить инструмент» + guardrails | `execute_with_guardrails` — единственная точка входа (065) |
| **Hands (sandbox)** | Исполнение эффекта; креды **никогда** не живут здесь | MCP-инструменты через `ToolRegistry` (070); code-exec — отдельная песочница |
| **Session** | Durable append-only лог **вне** окна контекста | LangGraph checkpointer (Redis, short-term) + long-term память (060) |

Следствие для ТЗ: harness — не «сервисный слой для удобства», а контракт с
чёткой ответственностью за RBAC, трассировку, guardrails и confidence gate.
Агент никогда не обращается к LLM/БД/инструментам напрямую — это ошибка
ревью (030.1, 050).

Второй принцип канона — **«начинай просто»**: не создавай агента, если
задачу решает workflow (фиксированный граф) без LLM-в-цикле. Многоагентность
оправдана только там, где нужна независимая декомпозиция и параллелизм
(canon A, *Building effective agents*).

## 2. Реестр агентов — 12 ролей, не 7

Черновик описывал 7 агентов с размытыми границами (Planner отдельно от
Router, Retriever совмещает поиск/код/SQL/API). Финальный реестр (000,
единственный источник истины) — точнее разделён по ответственности:

| Роль | Статус | Ответственность |
|---|---|---|
| `intent_classifier` | exists | Классификация намерения, temperature=0 |
| `supervisor` | exists | Декомпозиция и план. **Никогда не исполняет** |
| `researcher` | exists | Внешний поиск/извлечение через MCP |
| `critic` | exists | Quality gate перед финализацией |
| `formatter` | exists | MD/PDF/JSON форматирование |
| `memory_keeper` | exists | Semantic + episodic + graph память |
| `context_enricher` | merge | Бывшие ContextWeaver + Contextualizer |
| `text_ingestor` | planned | Чанкинг, нормализация при ингесте |
| `coder` | deferred | Код только в песочнице, по требованию |
| `analyst` | deferred | Анализ/тренды, по требованию |
| `planner` | merged → supervisor | Отдельно не создавать |
| `reasoner` | merged → critic | Отдельно не создавать |

**Отклонённые/переосмысленные роли черновика:**

- **Router** — не агент. Семантическая маршрутизация и cost-aware выбор
  модели — логика внутри `supervisor`/графа, не отдельный класс. Отдельный
  `RouterAgent` — ошибка ревью (000).
- **Graph Traversal Agent** — не отдельный агент. Multi-hop обход и
  комьюнити-суммаризация реализуются как MCP-инструмент `graph_query`
  (070), вызываемый `researcher`.
- **Learning Agent** — **не входит в реестр** в этой волне. Периодический
  fine-tuning ранжировщика/моделей — тяжёлая инфраструктура (отдельный
  training-pipeline, датасеты низкооценённых кейсов, MLOps), которая не
  оправдана до появления объёма продакшен-трафика. Рекомендация: держать
  как `deferred`-кандидата, реализовывать только по явному запросу и с
  отдельным решением по хранению/приватности обучающих данных (PII-риск
  выше, чем у обычной памяти, — cм. §6.5).

Новый узел графа = новая строка таблицы реестра 000; агент мимо реестра —
блокирующая находка при ревью.

## 3. Оркестрация (LangGraph)

`AgentState` — **единственное разрешённое место** для `TypedDict` во всём
проекте (010: исключение сделано ради LangGraph). Обязательные поля:
`trace_id`, `goal`, `plan`, `revisions_count`. Значения — только примитивы,
pydantic-модели (`AgentOutput` и подтипы) или UUID; сырые `dict`/`Any` в
state запрещены (050, 065).

Контракт узла — не бизнес-логика, а тонкая обёртка:

```
валидация входа → execute_with_guardrails(agent, input) → маппинг в state
```

`execute_with_guardrails` (единая точка, `domain/ports/harness.py`, 065)
внутри выполняет фиксированную последовательность: span узла → JIT-сборка
контекста → RBAC-фильтр инструментов → secret scan входа → `agent.run()` с
таймаутом из `AgentConfig` → `agent.verify()` → confidence gate → метрики.
Узел не повторяет ни один из этих шагов самостоятельно.

Циклы (Critic → доработка) ограничены `MAX_REVISIONS` из конфига (default
2) — защита от бесконечного цикла (050, 065); при исчерпании — эскалация,
не тихий выход.

## 4. Индексация и ингест

Реализуется через будущего `text_ingestor` (000: `planned`); ниже —
допустимые техники без изменения контракта:

- **Semantic/parent-child чанкинг**, при необходимости — Late Chunking
  (эмбеддинг всего документа перед нарезкой) — реализационная деталь, не
  архитектурное правило.
- **Contextual Retrieval** (Anthropic, Sep 2024): LLM генерирует короткое
  контекстное описание чанка, препендится перед эмбеддингом. Снижает
  retrieval miss — методика подтверждена каноном (см. B в `anthropic-canon.md`).
- Мультимодальность (OCR/VLM) — по необходимости, не блокирует базовую
  реализацию `text_ingestor`.
- Результат ингеста пишется **только** через `ingest_document` MCP-инструмент
  (070); если целевая система — EDMS, это write-операция → обязателен HITL
  (020, 070) и `irreversible=True` в `ToolDefinition`.

## 5. Поиск

**Решено (060.6), отклоняет черновик:** гибридный поиск = pgvector (cosine)
+ Postgres FTS (`tsvector` + `ts_rank_cd`), финальное ранжирование — по
importance. Называть это «BM25» в коде — ошибка; ParadeDB/`pg_search` и
прочие сторонние расширения — только после отдельного архитектурного
решения (000), не по умолчанию.

- Векторная БД — **только pgvector**, встроенная в существующие схемы
  `knowledge`/`memory`. Отдельный Qdrant не заводится без решения в 000
  (упрощение инфраструктуры: одна БД вместо двух движков).
- Reciprocal Rank Fusion при объединении вектор+FTS и Cross-Encoder
  reranking — реализационные детали, не противоречат правилам.
- `web_fallback` — последним по стратегии Supervisor'а (`RouteStrategy`,
  055), только если локальный поиск пуст; не `if` внутри агента-исполнителя.
- Кэширование частых запросов (CAG) — **не отдельный агент и не флаг в
  Router'е** (Router не существует). Если реализуется — это явная стратегия
  `RouteStrategy` в закрытом перечне `domain/policies/types.py` (055), с
  прописанным именем (например, `cached_response`), не скрытая эвристика.

## 6. Память — иерархия и обслуживание

### 6.1 Физическое разделение — без изменений от черновика, уже так и есть

Схема `knowledge` (эмбеддинг 1536d) — статичные знания; схема `memory`
(эмбеддинг 384d) — эпизодическая память. Связка «схема ↔ embedding-модель ↔
размерность» — единственный источник `core/types/embeddings.py` (060).
Смена модели эмбеддингов = отдельная миграция с reindex, не in-place.

### 6.2 Иерархия

| Уровень | Хранилище | TTL | Управляется |
|---|---|---|---|
| Short-term | LangGraph checkpointer (Redis) | `session_ttl_seconds` (конфиг) | авто |
| Medium-term | `memory.entries` (pgvector) | 30 дней (конфиг) | MCP `save_memory` |
| Long-term | граф знаний (Neo4j/Cognee) | бессрочно, растёт только через consolidate | consolidation |

Стек памяти — **LangMem (эпизодическая) + Cognee (графовая long-term)**,
уже принят в `099-project-map.mdc`; черновик совпадает с финальным решением,
изменений не требуется.

### 6.3 Обслуживание

Sliding window, рекурсивная суммаризация (~20 оборотов, константа конфига),
forgetting curve, приоритизация по `recency + relevance + access_frequency`
— формула в одном месте (`domain/memory/scoring.py`) — всё уже закреплено в
060 в тех же терминах, что и в черновике.

### 6.4 xMemory (decouple-before-aggregate) — рекомендация, не обязательство

Идея черновика — сначала изолировать переиспользуемые факты/обновления из
похожих эпизодов и только затем агрегировать их в группы для поиска —
концептуально совместима с текущим шагом consolidation (060: эпизод с
`access_frequency ≥ N` и `importance ≥ M` конвертируется в узел графа).

**Рекомендация:** не реализовывать как отдельный алгоритм в первой волне.
Текущая consolidation-схема проще и достаточна для старта; xMemory-паттерн
стоит вернуть как оптимизацию, когда появятся метрики (`palatium_memory_*`,
040), показывающие избыточность/шум в извлекаемом контексте. Если решаете
внедрять раньше — это правка `domain/memory/consolidation` с отдельным
ревью, не тихое добавление в существующий пайплайн.

### 6.5 Безопасность памяти

Row-Level Security по `user_id` на `memory.entries` обязателен, без
`BYPASSRLS` у app-роли (060). Перед записью в medium/long-term — secret
scanner (020) + PII-классификация; PII в long-term — только с
`contains_pii=true` и правилом забывания, молчаливая запись PII запрещена
(060.8). Это особенно важно, если когда-либо будет реализован Learning
Agent (§2): обучающие данные из истории диалогов — PII по определению,
отдельное согласие/retention-политика обязательны до, а не после запуска.

## 7. Контекст-инжиниринг

Пайплайн `ContextBuilder`: **извлечение → фильтрация → ранжирование →
сжатие → доставка** (065). JIT — загружаются только ключи, объявленные
`agent.get_required_context_keys()`; агент не дособирает контекст внутри
`run()` (030.2). Нехватка ключа — ошибка сборки, не тихий пропуск.

Прогрессивное раскрытие для скиллов: заголовок `SKILL.md` — всегда в
контексте; `reference.md` — только через tool call `skill_reference(name)`,
проходит RBAC и трассировку как обычный вызов инструмента (065). Это тот
же принцип, что и progressive disclosure в MCP (canon D, *Code execution
with MCP*): не грузить всё в контекст заранее.

Компакция — `ContextBuilder.compact()` при 80% лимита модели (лимит — из
`core/types/model_registry.py`, не хардкод). При компакции `goal`, `plan` и
последние результаты **сохраняются отдельно** в long-term память, не
сжимаются вместе с диалогом (060.9, 065.3) — потеря цели при компакции
недопустима (canon C, *Effective harnesses*: «premature done» и «dirty
handoff» — прямое следствие потери state).

## 8. Harness и Zero Trust

RBAC-проверка — **одна точка**: `ToolRegistry` при резолве инструмента, до
вызова. Harness не дублирует проверку — только передаёт вызов дальше (020).
Отказ RBAC — не исключение наружу, а структурированный `AgentOutput(status=
"failure", error_message=...)` + audit-событие `permission_denied` (020,
030.8, 070).

Containment — два независимых слоя (canon F, *Contain Claude* / *Beyond
permission prompts*), оба обязательны, а не взаимозаменяемы:

1. **Supervision** — HITL-разрешения на уровне действия (§9).
2. **Containment** — изоляция файловой системы и сети для sandbox
   выполнения кода; креды **никогда** не попадают внутрь sandbox (только
   через прокси/vault снаружи).

Секреты никогда не логируются и не попадают в промпт; сканирование
паттернов централизовано в `core/security/secret_scanner.py`, вызывается
из harness перед LLM и перед логированием (020).

## 9. HITL

Обязателен для: email, запись/изменение/удаление в БД/FS/EDMS, мутации
графа знаний, внешние write-вызовы, финансовые операции, доступ к PII,
произвольный код, и **любое действие с confidence < порога** (020).

- Выбор пользователю — только кликабельные карточки с уникальным `card_id`,
  TTL по классу действия (обратимое — 30 мин, необратимое — 5 мин),
  idempotency key на ответ.
- Карточка одноразовая — повторный ответ на тот же `card_id` отклоняется
  независимо от TTL; проверка состояния — по Redis (source of truth), не
  по UI.
- `risk_score` вычисляется из класса действия + confidence, не хардкодится;
  выше порога → эскалация к менеджеру, иначе — auto-reject с понятным
  сообщением.
- LangGraph: **`interrupt()` внутри узла + `Command(resume=...)`**.
  `interrupt_before` — устаревший API, запрещён (020).

Auto-approve допустим только для low-risk стратегий из закрытого перечня
(`ack_only`, `format_only`, `small_talk`, 055) — никогда для финансов/PII/
code-exec, вне зависимости от уверенности классификатора (canon F, *Auto
mode*: классификатор промахивается именно на объёме согласия vs реальный
радиус поражения).

## 10. Отказоустойчивость

- **Circuit Breaker**: closed → open → **half-open** (пробный вызов после
  cooldown) → closed. Без half-open — не считается breaker'ом (020). Порог
  сбоев и cooldown — из конфига, не «после 3 fail» захардкожено.
- **Kill Switch**: глобальный флаг в Redis; новые запуски графа отклоняются,
  in-flight узлы завершают текущий шаг и останавливаются на границе узла;
  каждое переключение — в audit (020).
- **LLM fallback** — минимум 2 независимых провайдера (LiteLLM или
  аналог), не один провайдер с retry.
- Retry — экспоненциальный backoff + jitter на всех внешних вызовах
  (`core/resilience`), не самописный per-агент код.

## 11. MCP и инструменты

Канонический закрытый перечень (070) покрывает всё, что нужно черновику:
`search_knowledge`, `search_memory`, `save_memory`, `forget_memory`,
`consolidate_memory`, `ingest_document`, `graph_query`, `web_fallback`.
Новый инструмент — правка перечня + обсуждение, не ad-hoc регистрация.

- `ToolDefinition` — frozen pydantic input/output схемы + одна метка
  `ToolPermission` из закрытого перечня (`memory.read`, `memory.write`,
  `knowledge.read`, `graph.query`, `document.ingest`, `web.access`).
- ≤5 инструментов на агента; больше — обоснование комментарием в
  `config.py` (050, 070). Инструменты — немного, высокоценные, не 1:1
  обёртки над API (canon D, *Writing effective tools*): `search_knowledge`
  лучше, чем `list_documents` + `get_document` + `filter_documents`.
- Прямой доступ агента к БД/HTTP мимо MCP — ошибка ревью (050, 070); все
  внешние вызовы — только через MCP-инструменты или порты.
- Параметризованные запросы всегда: Cypher — через `$param` плейсхолдеры,
  SQL — через параметры драйвера. Конкатенация строк запроса — критическая
  уязвимость.
- Прогрессивное раскрытие инструментов (canon D, *Advanced tool use*):
  не грузить определения всех tools в контекст сразу — держать «горячими»
  часто используемые, остальное — по запросу/discovery.

## 12. Observability

- **Primary — OpenTelemetry**; LangSmith (если включён) — вторичный
  экспортёр через OTel, не отдельные `@traceable`-декораторы (040).
- 100% узлов StateGraph — под span'ом; каждый LLM-вызов и tool call —
  дочерний span. Правило «никогда потом»: span и хотя бы одна метрика
  добавляются одновременно с новым узлом, не отдельной задачей.
- Метрики — из единого реестра `palatium_*` (040): длительность,
  token usage, ошибки, эскалации, cost, RBAC-отказы, replay HITL-карточек,
  состояние circuit breaker, память (`recall_at_k`, latency, размер записи).
- **Hash-chained audit log**: canonical JSON, `current_hash = sha256(
  previous_hash + sha256(canonical_json(payload)))`, genesis-запись
  зафиксирована вне БД; append-only на уровне прав БД (не только кода);
  периодическая верификация цепочки — минимум раз в сутки.
- **LLM-as-a-Judge** — quality gate перед финализацией критичного выхода;
  судья — модель другого провайдера, чем генератор. `accuracy < 6/10` или
  `safety < 8/10` → `requires_review = true`. Нужен ли Judge вообще —
  решает `CriticPolicy` (055): low-risk стратегии проходят без судьи, все
  остальные — обязательно.
- RAGAS-метрики черновика (Faithfulness, Answer Relevancy, Context
  Relevancy) не заводятся отдельным пайплайном — они формулируются как
  дополнительные критерии **внутри промпта существующего Judge**, если
  нужна более тонкая оценка ответа на основе retrieved-контекста.

## 13. Тестирование и evals

Пирамида (075): unit (моки harness/LLM, проверка контракта, не реализации)
→ policies (`domain/policies/`, чистые unit без LLM, coverage ≥ 90%) →
интеграционные (полный граф на cassette-LLM, живые LLM — только
`@pytest.mark.llm_live`) → evals (`tasks.json` + `grader.py` по единому
Protocol, деторминированные в PR, LLM-judge — nightly) → нагрузочные
(`@pytest.mark.slow`).

`evals/baseline.json` — в репозитории, обновляется осознанно в том же PR,
что улучшение; ночное падение → задача на разбор, не авто-revert. Тесты
никогда не ослабляются, чтобы «прошли» (050, 075) — это canon G
(*Demystifying evals*): eval — это модель **+ harness** вместе, регрессия
harness'а не должна маскироваться под «модель поглупела».

| Векторный + лексический поиск | pgvector + Postgres FTS | принято, ParadeDB отклонён |
| Графовая БД | Neo4j | принято |
| Переранжирование | Cross-Encoder (модель — по бенчмарку, не хардкод) | реализационная деталь |

## 15. Целевые метрики (SLO, ориентир не гарантия)

| Метрика | Целевое значение |
|---|---|
| Memory Recall@k | > 85% |
| Memory query latency p95 | < 200 ms |
| Agent success rate (confidence ≥ порога) | > 95% |
| Circuit breaker false-open rate | ~0 (проверяется drill'ом) |
| Audit chain verification | 100% проходит ежедневно |
| Coverage `domain/policies` | ≥ 90% |
| Benchmark success rate (100+ задач) | > 85% |

Цифры из черновика («67% → 8% перепромптинга», «91.4% cross-session
recall») — маркетинговые ориентиры сторонних систем 2026 года, не
проверенные на этом проекте цифры; не закладывать как контрактные SLO без
собственного бенчмарка.

## 17. Зафиксированные решения по открытым вопросам

Из четырёх пунктов, ранее вынесенных на решение пользователя:

1. **Learning Agent** — не добавляется в реестр в этой волне (deferred,
   вне scope; см. §2, §6.5 про PII-риск обучающих данных).
2. **xMemory consolidation** — не реализуется как отдельный алгоритм
   сейчас; остаётся рекомендацией на будущее при появлении метрик
   избыточности (§6.4).
3. **RAGAS-критерии** — не отдельный пайплайн; допустимы как
   дополнительные пункты промпта существующего LLM-as-a-Judge (§12).
4. **CAG/prompt-кэширование** — не реализуется через несуществующего
   Router-агента; при необходимости — именованная `RouteStrategy` в
   закрытом перечне `domain/policies/types.py` (§5, 055).

Если по любому из пунктов 1–4 решение должно быть другим — это правка
данного документа **и** соответствующего правила (000/055/060/040), не
тихое расхождение между ТЗ и кодом.

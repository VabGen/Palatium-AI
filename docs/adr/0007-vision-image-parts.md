# 0007. Vision: изображение как часть сообщения, а не base64 в тексте и не OCR-подмена

- **Статус:** accepted (2026-10-25) — S2a контракт/политика, S2b маршрут и S2c канал
  доставки (`AgentInput.image_parts` → граф → LLM) реализованы; vision-eval (S3) добавлен
  как opt-in live-тест
- **Дата:** 2026-10-25
- **Правило-владелец:** 010, 020, 060, 070; план — `.cursor/plans/canvas-vision-phase-7.md`

## Контекст

`ChatMessage.content` — строка (`domain/llm/models.py`): LLM получает только текст.
Изображение, приложенное к сообщению, идёт через attachment pipeline
(scan → parse → OCR → prompt-injection gate → fence), и в модель попадает распознанный
текст. Визуальная семантика — график, схема, макет, подпись, таблица-картинка — теряется;
при пустом OCR модель не видит ничего и не может это сказать.

## Конфигурация (подтверждена владельцем 2026-10-25)

| Параметр | Значение | Смысл |
|---|---|---|
| `LLM_VISION_MODEL` | `vision-tier` | алиас vision-capable модели на corporate gateway |
| `LLM_VISION_MAX_IMAGE_BYTES` | `10485760` | потолок на одно изображение после `stat` |
| `LLM_VISION_MAX_IMAGES` | `4` | изображений на один chat-вызов |
| `ALLOW_PII_IMAGES` | `False` | owner-opt-in: пропускать ли изображения с `contains_pii` в модель |
| fallback для vision | **нет** | vision-вызов не уходит на текстового провайдера |

Почему без fallback: алиас принадлежит одному провайдеру. Фоллбэк на текстовую модель
не «деградирует» ответ, а **искажает** его — модель уверенно отвечает про картинку,
которую не видела, либо падает на неподдерживаемом payload. Честный типизированный
отказ лучше правдоподобной ошибки (035, 055).

## Решение

1. Контракт расширяется **аддитивно**: `ChatMessage.image_parts: tuple[ImagePart, ...] = ()`,
   где `ImagePart` — `attachment_id` + `mime`.
   `content` остаётся `str`; base64/data URL в тексте не появляются.
   - Почему не `content: str | list[Part]`: ломает каждого потребителя `ChatMessage`
     (агенты, ключи кэша, токен-подсчёт, логи, тесты) — молчаливая миграция всех адаптеров.
   - Изображения допустимы только на `role="user"`: system/assistant-картинка обошла бы
     prompt-injection gate, который принадлежит attachment pipeline (020).
   - Доступ решается одной доменной политикой `VisionPolicy`
     (`domain/policies/vision.py`): mime whitelist → размер → PII → наличие алиаса;
     причина отказа — один Literal, а не флаг «попробуем».
2. Байты резолвит **отдельный порт** `VisionImageSourcePort`
   (`domain/ports/vision.py`), реализация — `BlobVisionImageSource` поверх
   `BlobStorePort`. Порт, а не прямой blob в адаптере: LLM-слой не знает про ключи
   вложений, а тесты подменяют один шов вместо SDK.
   - Ключ — `AttachmentIntakePolicy.blob_key(attachment_id)`, не имя файла (no traversal).
   - MIME и размер берутся из `BlobStorePort.stat`, а не из клиентского заявления;
     несовпадение с `ImagePart.mime` — отказ (тампера), не конвертация.
   - Потолок байтов применяется дважды: к `stat` (дешево) и к прочитанному payload
     (лгущий stat не покупает безлимитную загрузку).
   - Decode guard (`image_decode_guard`) — до base64, чтобы decompression bomb
     отвалился у нас, а не внутри вызова провайдера.
3. `VisionPolicy` вызывается **до** чтения байтов, на уровне сборки частей:
   `VisionImageService` (`application/services/vision_images.py`) получает строки
   вложений одного владельца (`user_id` обязателен), читает `contains_pii` из строки
   (классификация сделана пайплайном, который сканировал контент) и возвращает
   `parts` + `denials` с типизированными причинами. Отказ по PII не «пропускается»,
   а попадает в `denials` и в метрику `palatium_vision_image_total`.
   Тот же сервис обслуживает канал доставки: `parts_for_blocks()` решает по блокам
   текущего хода (mime/размер — из blob `stat`, `contains_pii` — из строки), один
   цикл отбора на оба входа (050).
3a. **Канал доставки (S2c, 2026-10-25):** `AgentInput.image_parts: tuple[ImagePart, ...]`
   (`domain/agents/messages.py`, аддитивно, default `()`); граф решает один раз на входе
   (`IntentGraphRunner._admitted_image_parts` → `AgentGraphState.image_parts`), узлы
   Researcher/Analyst передают набор в LLM-вызов, изображения едут на `role="user"`.
   Отдельный `AttachmentPayload` не вводится: `ImagePart` уже несёт UUID + закрытый
   mime-словарь, второй DTO рядом — второй источник истины (050).
3b. **PII-исключение:** `ALLOW_PII_IMAGES=true` (default `false`) пропускает
   PII-изображение в модель, но **каждое** такое событие аудируется: span event
   `gen_ai.pii_image_allowed`, метрика `palatium_vision_image_total{reason="pii_allowed"}`,
   warning-лог. Флаг — решение владельца данных, не «настройка удобства» (020/060).
4. OCR не удаляется и не подменяется: он остаётся дешёвым первым проходом и единственным
   путём для моделей без vision (`ATTACHMENTS_IMAGE_OCR_MODEL` — отдельный алиас OCR-пути).
5. Модель без vision обязана **явно отклонить** `image_parts` типизированной ошибкой, а не
   молча отбросить картинку (035: fail-closed на границе). Ошибки:
   `VisionUnsupportedError` (нет алиаса/источника, провайдер без vision) и
   `VisionImageUnavailableError` (blob исчез, mime не совпал, размер выше потолка).
6. Vision-модель адресуется отдельным значением конфига, а не «frontier по умолчанию»:
   цена vision-токенов другая, и tier агента не должен её менять неявно. Адаптер
   игнорирует `model` агента, если у сообщения есть `image_parts`.
7. Fallback-цепочка для изображений состоит из одного звена — primary. Это правило
   живёт в `_FallbackChainLLMAdapter` (`generate` / `generate_stream`), а не в агенте:
   решение принимается по наличию частей, а не по имени модели.

## Рассмотренные альтернативы

- **base64 / data URL внутри `content`** — отвергнуто: невалидируемо типом, раздувает
  токены и логи, картинка протекает в трассы и audit (020, 040).
- **OCR-only как окончательное решение** — отвергнуто: теряет визуальные классы
  (графики, схемы, таблицы-картинки). Остаётся fallback, не заменой.
- **Отдельный vision-агент или MCP-инструмент** — отвергнуто: это ось сообщения, а не
  задача; новый агент = новый узел графа без потребности (000).
- **Fallback vision → text-модель** — отвергнуто владельцем: искажение результата
  вместо честного отказа.

## Последствия

- LLM-порт расширяется аддитивно; адаптеры без поддержки vision отклоняют `image_parts`
  явно, а не игнорируют.
- Нужен vision-eval (075): «картинка с графиком → корректное описание», «нечитаемая
  картинка → честный отказ», «PII на картинке → маскирование/отказ», а не только
  текстовые кейсы (S3).
- Стоимость: vision-токены через существующий CostTracker (Phase 3), отдельная строка
  бюджета; `LLM_VISION_MAX_IMAGES` ограничивает всплеск на один ход.
- Клиентская сторона закрыта в S2c: `AgentInput.image_parts` несёт одобренные
  `ImagePart` из графа в LLM-вызов; сам `AgentInput` — строгая pydantic-модель 030,
  `context` остаётся `dict[str, str]` для остальных данных.

## Открытые вопросы

1. **Алиас vision-модели** — закрыт 2026-10-25: `vision-tier` на gateway, fallback
   выключен (см. §Конфигурация).
2. **PII:** закрыт 2026-10-25 решением владельца — конфиг-флаг `ALLOW_PII_IMAGES`
   (default `false`). При `false` поведение прежнее (`pii_blocked`, документы с PII идут
   по OCR + HITL); при `true` изображение уходит с обязательным аудитом
   (`gen_ai.pii_image_allowed`, `reason="pii_allowed"`, warning). Молчаливого пропуска
   PII нет ни в одном режиме.
3. **Vision-eval (S3):** живой gateway-тест добавлен — `tests/eval/test_vision_live.py`
   (маркер `live`, вне CI; запуск в docstring).

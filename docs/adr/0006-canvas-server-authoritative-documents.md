# 0006. Canvas = server-authoritative `ContentDocument`; Yjs CRDT отклонён

- **Статус:** accepted
- **Дата:** 2026-10-25
- **Правило-владелец:** 000, 065, 050; план — `.cursor/plans/canvas-vision-phase-7.md`

## Контекст

Роадмап Phase 7 предполагал «Yjs CRDT» как основу Canvas. Фактическое состояние кода
этому не соответствует и не требует этого:

- ответ платформы — один контракт `ContentDocument` с 12 типизированными блоками,
  включая артефактные `TableBlock`, `ChartBlock`, `WidgetBlock`
  (`domain/content/content_document.py`), рендер — единый `BlockRenderer`
  (`web/src/components/BlockRenderer.tsx`);
- идентичность ответа и diff ревизии — content-hash, а не id от модели
  (`domain/content/revision.py`, `DocumentRevision` в payload хода);
- содержательная правка ответа — это reject → новый turn (`revision_feedback` →
  `RevisionPolicy` → Formatter), а не посимвольное редактирование документа;
- доставка — односторонний SSE (`docs/architecture/streaming.md`), тред принадлежит
  одному владельцу (owner scope, 060).

Сценария одновременного редактирования одного документа двумя людьми в продукте нет.
Yjs добавил бы **третье** состояние документа (CRDT-лог) рядом с `ContentDocument` и
persisted turn payload — то есть два источника истины о том, что видит пользователь.

## Решение

1. Canvas-артефакт — это `ContentDocument`. Отдельного canvas-движка, второй схемы
   документа или второго рендерера не появляется.
2. Интерактив выражается существующими примитивами: `WidgetBlock` (opaque
   `kind` + `ref_id`, ссылка только absolute http(s)) и `ActionSpec` / HITL-карточки —
   не исполняемым клиентом кодом из модели.
3. Любая содержательная правка — новый серверный документ: `revision_feedback` →
   Formatter → `DocumentRevision`. Клиент не мутирует блоки «в документе»; источник
   истины остаётся серверным.
4. Yjs, y-websocket, y-prosemirror/tiptap, awareness-протокол не вводятся.

## Рассмотренные альтернативы

- **Yjs CRDT (y-prosemirror / tiptap)** — отвергнуто: нет сценария co-editing, зато
  появляется второй канал состояния (бинарный WS рядом с SSE + persist), лог
  CRDT-апдейтов не описывается content-hash'ем → история и разметка ревизии расходятся,
  плюс новые зависимости и миграция фронта. Цена платится за несуществующее требование.
- **Отдельная canvas-схема/движок рядом с `ContentDocument`** — отвергнуто: второй
  контент-контракт (050); тот же класс решения уже отклонён ADR 0005.
- **Клиентские правки блока с последующей синхронизацией** — отвергнуто: обходит
  серверные инварианты (валидация блоков, grounding/citations, secret scan и PII-гейт на
  выходе — 020/060).

## Последствия

- Проще: один контент-контракт, одна ревизионная ось, один транспорт; фронтовый бандл
  не растёт на CRDT-стек.
- Дороже: нет simultaneous/offline editing; правка абзаца — регенерация документа
  (так работает и сейчас; бюджет длины — W7a).
- Если появится реальное требование co-editing — это **новый ADR**, а не дополнение
  0006: решение меняется новым решением, история компромисса сохраняется (086).

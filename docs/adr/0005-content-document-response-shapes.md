# 0005. Единый `ContentDocument` + ось `response_shape` вместо схемы и рендерера на сценарий

- **Статус:** accepted
- **Дата:** 2026-10-19
- **Правило-владелец:** 000, 030, 055; план — `.cursor/plans/response-shapes.md`

## Контекст

Ответы платформы визуально нестабильны: одна и та же по смыслу просьба приходит то
прозой, то структурой, а явный запрос формы («покажи таблицей», «по шагам») не доезжает
до генератора как типизированная ось. Предлагалось завести отдельную Pydantic-схему,
детерминированный рендерер и строку в `PIPELINES` на каждый сценарий
(`ComparisonTable`, `SingleDocumentAnalysis`, `BulletedPlan`, `ProseFallback`).

В репозитории уже есть `ContentDocument` (`domain/content/content_document.py`):
12 типизированных блоков, `schema_version`, валидация таблиц/чартов, единый
`BlockRenderer` на фронте и schema-first генерация в Formatter'е. Роутинг принадлежит
`ExecutionPlanner`, а не таблице пайплайнов.

## Решение

1. `ContentDocument` остаётся **единственным** контент-контрактом ответа.
2. «Сценарий» выражается **композицией существующих блоков**, а не новой top-level
   схемой: сравнение — `TableBlock` + `ParagraphBlock`/`CalloutBlock`, план —
   `StepsBlock`/ordered `ListBlock`, анализ документа — `HeadingBlock` +
   `ParagraphBlock` + `CalloutBlock` (risks), проза — `ParagraphBlock`.
3. Добавляется ось `ResponseShape` (`auto`, `comparison_table`,
   `document_analysis`, `plan`, `prose`) — **форма** тела ответа, ортогональная
   `task_kind` и маршруту. Дефолт `auto` сохраняет текущее поведение.
4. Ожидаемая композиция и её проверка живут в одной чистой политике —
   `ShapeRecipePolicy` (`domain/policies/shape.py`); рендерер форму не валидирует.
5. `choice_cards` / `greeting` в ось не входят: они уже выражены
   `requires_user_choice` и `task_kind=social_conversation` + `style_hint`.
6. Новый визуальный примитив, не выразимый блоками, добавляется как значение
   `ContentBlock` (одно расширение контракта), а не как второй документ.

## Рассмотренные альтернативы

- **Схема + рендерер на сценарий** — отвергнуто: второй контент-контракт рядом с
  `ContentDocument` (050), дублирование рендеринга (блок-рендерер уже детерминирован),
  N схем вместо одного расширяемого union, расхождение при каждом новом сценарии.
- **`PIPELINES`-таблица маршрутов** — отвергнуто: второй источник истины рядом с
  `ExecutionPlanner`; маршрут зависит от `requires_mcp`, grounding, attachments и
  rollout-гейтов, которые таблица не видит.
- **Слить `researcher` и `formatter` в один `schema_fill`** — отвергнуто: нарушает
  разделение «добыть / оформить» (030) и лишает Critic материала проверки; экономия
  одного вызова не окупает потерю контракта.
- **Пост-обработка markdown в блоки** — отвергнуто: форма тогда определяется
  эвристикой парсера, а не контрактом; именно это сегодня даёт визуальную замену.

## Последствия

- Новый сценарий = рецепт формы (и, при необходимости, новый тип блока), а не
  схема + рендерер + строка роутера.
- Ответ при `auto` не меняется: ось не обязательна для существующих вызовов.
- `ShapeRecipePolicy` даёт метрику соблюдения формы, но в волне 1 **не** блокирует
  ответ: mismatch — презентационный сигнал, а не потеря контента.
- Отдельной задачей остаётся стриминг типизированных блоков (`partial_document`) —
  без него финальный документ всё ещё приходит одним кадром после markdown-превью.
- Per-scenario схемы могут вернуться только новым ADR, superseding этот.

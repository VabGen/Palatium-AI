# Code Revision — ZeroTrust Agent Platform

Проверяй код по этому чек-листу, в этом порядке. Для каждого пункта выноси явный вердикт
`OK` / `WARN` / `BLOCK` с конкретной строкой файла.

## 1. Архитектура (BLOCK при нарушении)
- Домен не импортирует инфраструктуру/SDK напрямую (см. `000-architecture.mdc`).
- Агент реализует ровно одну роль из реестра 12 агентов, не смешивает ответственности.
- Supervisor/Planner не содержат в `allowed_tools` инструментов исполнения.

## 2. Типизация (BLOCK при нарушении)
- Нет `Any`, непараметризованных `dict`/`list`.
- Все I/O — Pydantic-модели, есть `Field(...)` ограничения на числовых/строковых полях.
- Пройдёт ли `mypy --strict`? Если сомнительно — явно укажи, где именно упадёт.

## 3. Безопасность / HITL (BLOCK при нарушении)
- Есть ли действие из списка (email, db-write, финансы, PII, code-exec)?
  → должен быть `interrupt_before` / HITL-карточка перед выполнением.
- RBAC allow-list проверяется до вызова инструмента, а не после.
- Нет секретов в коде/логах/промптах (regex-паттерны `sk-`, `AKIA`, `password=`).

## 4. Отказоустойчивость (WARN при отсутствии)
- Timeout задан (default 300s), retry с backoff (default 3 попытки).
- Confidence threshold проверяется перед возвратом успеха.
- Есть fallback-модель / fallback-путь при сбое инструмента.

## 5. Observability (WARN при отсутствии)
- Узел обёрнут трассировкой.
- Есть минимум одна Prometheus-метрика на узел.
- Критичное действие пишет запись в audit log.

## Формат вывода ревью

```
### Вердикт: [ready to merge | needs changes | blocked]

BLOCK:
- <файл>:<строка> — <проблема> → <как исправить>

WARN:
- <файл>:<строка> — <проблема> → <рекомендация>

OK:
- <что уже сделано правильно, кратко>
```

Не переписывай весь файл молча — сначала вердикт, изменения только по запросу пользователя
или для BLOCK-пунктов, которые нельзя смержить как есть.

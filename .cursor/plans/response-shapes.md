# Response shapes — ось формы ответа поверх единого `ContentDocument`

Спецификация решения «структурированный ответ для любого сценария». Норму не
дублирует: контракт UI-документа — `domain/content/content_document.py`, стриминг —
`.cursor/plans/structured-streaming.md`, архитектурное основание — ADR 0005.
Статус: волна 1 (ось + политика) — реализована; волны 2–4 — открыты.

## 1. Проблема

«Красивый структурированный ответ» нельзя получить просьбой к LLM «пиши красиво»:
форма плавает между ходами, а финальный `ContentDocument` заменяет показанный
markdown-превью (layout shift). Предложение «своя Pydantic-схема на каждый сценарий
+ свой рендерер + свой PIPELINES» решает форму, но создаёт **второй контент-контракт**
рядом с `ContentDocument` (12 типизированных блоков, `schema_version`, валидация
таблиц/чартов) и второй источник роутинга рядом с `ExecutionPlanner`.

Наблюдаемые следствия, которые надо убрать:

- форма ответа непредсказуема: сравнение может прийти прозой, план — абзацами;
- пользователь просит «таблицей», а платформа отдаёт пересказ (просьба не доезжает
  до генератора как типизированная ось, только как строка в тексте);
- превью и финал рисуются разными механизмами (markdown → блоки).

## 2. Scope

- Ось `ResponseShape` в реестре осей `domain/policies/types.py`.
- Поле `response_shape` в `IntentClassifierOutput` + правило в промпте классификатора.
- Протаскивание оси: `ContinuityPolicy` (`EffectiveRoutingIntent`) → `ContextPacket`
  → `FormatterAgent` (payload + промпт схемы).
- `ShapeRecipePolicy` (`domain/policies/shape.py`): рецепт формы (что требовать от
  документа) + детерминированная проверка готового `ContentDocument` → `ShapeVerdict`.
- Метрика `palatium_response_shape_total{shape, outcome}` в реестре 040.
- Тесты: политика, парсинг оси, pass-through continuity, дефолт `auto`.

## 3. Вне scope

- Новые top-level Pydantic-схемы (`ComparisonTable`, `BulletedPlan`, `ProseFallback`).
  Их роль выполняют композиции существующих блоков (`TableBlock`, `StepsBlock`,
  `ListBlock`, `ParagraphBlock`, `HeadingBlock`, `CalloutBlock`).
- Новый роутер `PIPELINES`. Маршрутизация остаётся в `ExecutionPlanner`.
- `partial_document` / типизированные partial-блоки в SSE и React-рендер — волна 2.
- `rerender_from_memory` (0 LLM) и style presets — волна 3.
- Repair-проход при несоответствии формы — волна 2 (в волне 1 mismatch только
  измеряется и логируется, ответ не блокируется и не переписывается).
- Память `kind="comparison_result"` — не вводится: документ уже персистится в
  payload хода (`intent_turn_helpers.assistant_turn_payload`).

## 4. Решения

### 4.1 Одна схема ответа, много рецептов формы

`ContentDocument` остаётся единственным контент-контрактом. «Сценарий» — это
композиция блоков, а не новая схема. Новый блок вводится только тогда, когда
существующие не выражают визуальный примитив (например, diff-view), и это изменение
`ContentBlock`, а не второй документ.

Отвергнуто: per-scenario схемы + per-scenario рендереры — два контент-контракта
разъедутся (050), а `BlockRenderer` уже детерминированно рисует по типу блока.

### 4.2 `ResponseShape` — ось формы, не маршрута

Закрытый Literal (`010`): `auto`, `comparison_table`, `document_analysis`, `plan`,
`prose`. Дефолт `auto` — поведение не меняется, пока форма не названа.

- `choice_cards` / `greeting` **не** входят в ось: это уже выражено
  `requires_user_choice` / `task_kind=social_conversation` + `style_hint`. Дубль
  создал бы два источника истины (050).
- Ось не влияет на `ExecutionPlanner`: `response_shape` не выбирает researcher/tool.
- `resolve(shape, task_kind)` возвращает `None` для `auto`, `social_conversation` и
  `clarification_needed` — у этих ответов нет содержательного body, форма к ним
  неприменима.

### 4.3 Проверка формы не блокирует ответ

`ShapeRecipePolicy.validate` — чистая функция над готовым документом. Возможные
исходы: `satisfied` / `mismatch` (метрика) и стабильный `reason`-код для логов.
В волне 1 mismatch **не** понижает
`status`, не поднимает `requires_review` и не запускает второй LLM-вызов: контент
корректен по Pydantic, форма — презентационная преференция. Метрика показывает долю
несоблюдённых явных запросов; repair появится в волне 2 вместе с partial-блоками.

### 4.4 Форма задаётся промптом, а не пост-обработкой

`response_shape` едет в payload Formatter'а и раскрывается статической секцией
промпта (для `json_schema` — композиция блоков, для legacy-markdown — GFM-аналог).
Промпт остаётся константой в `prompts.py`; динамической сборки промпта нет (030).

### 4.5 Детерминированные обходы LLM уважают форму

Явная форма — это запрос на композицию, поэтому три «дешёвых» пути её не обходят:

- `FormatterFastPathPolicy`: `response_shape != auto` — hard stop (passthrough
  эмитит только абзацы и молча проигнорировал бы таблицу/шаги).
- L1 response cache: для `response_shape != auto` не используется — ключ не содержит
  форму, а кэшированный эхо-ответ обошёл бы и проверку формы.
- Ранний draft из `worker_summary` не стримится при явной форме: он гарантированно
  будет заменён финальным документом — ровно тот layout shift, который убирает ось.
  Ранняя отрисовка возвращается в волне 2 типизированными partial-блоками.

## 5. Волны

| Волна | Содержание | Статус |
|---|---|---|
| 1 | Ось `ResponseShape` end-to-end, `ShapeRecipePolicy`, промпт-секции, метрика, unit-тесты | сделано |
| 2 | `partial_document` (типизированные блоки в SSE), `BlockRenderer` как единственный превью, метрика `palatium_sse_layout_shift_total{contract="structured_incremental"}=0` | сделано |
| 2b | repair формы один раз — **отложен**: после `block_delta` он заменяет уже показанные блоки (см. §8) | открыто |

| 4 | Расширение рецептов (новые формы только при доказанной потребности), удаление legacy-пути | открыто |

## 6. DoD волны 1

1. `IntentClassifierOutput.response_shape` валидируется закрытым Literal; неизвестное
   значение → `auto`, а не ошибка парсинга.
2. Ось доезжает до `FormatterAgent` через `ContextPacket` (не через повторный разбор
   текста пользователя).
3. `ShapeRecipePolicy.resolve` покрывает все значения оси; `validate` даёт стабильные
   reason-коды для метрики/логов.
4. Промпты Formatter'а содержат правила для каждой формы; `auto` ничего не навязывает.
5. Метрика зарегистрирована в `core/observability/metrics.py` (новых имён вне реестра нет).
6. Дефолт не меняет поведение: при `auto` ни один существующий вызов не обязан
   передавать новое поле.

## 7. Enforcement

- `ResponseShape` объявлен один раз — `domain/policies/types.py`; локальные Literal
  в агентах запрещены (055).
- `ShapeRecipePolicy` — единственное место проверки композиции; рендерер блоков
  не дублирует семантические проверки.
- Гейты: `scripts/ci_quality.py` (ruff/mypy), unit-тесты политики; автоматического
  гейта «форма соблюдена» нет — это метрика, а не блокирующее условие.

## 8. Открытые вопросы

- Нужен ли `response_shape` в `Evaluations`/judge как отдельная ось качества — решить
  после накопления статистики волны 1.
- Repair-стратегия волны 2 (решено 2026-10-19): **пост-стрим repair не делаем**.
  После `block_delta` блоки уже прочитаны пользователем, а любой повторный вызов,
  меняющий композицию, — это `replace` под `structured_incremental`, т.е. ровно
  тот layout shift, который волна 2 запрещает (DoD: счётчик = 0). Mismatch остаётся
  метрикой: если статистика покажет, что причина систематически в модели, повторная
  генерация должна выбираться **до** первой отрисовки (отдельный эксперимент/флаг),
  а не после. Детерминированная перекомпоновка блоков отклонена по той же причине.
